## 二、工程上的取舍（界面）

- `x` 对已结束的行只是不再列，通讯录里照旧在，模型照样能发消息叫它接着干；通讯录里真正去掉要连同下层释放运行面，界面上没有给这一步。
- 进入子 agent 的会话时，消息区先放它会话记录里的历史，再接实时；还没开运行面的（续接认回、没收到过消息的）只有历史，打字即重开。
- 退出确认写在状态行（与单按 Ctrl+C 的退出提示同一处），只等下一个键：`y` 与 Enter 退出，别的键取消；确认期间再要求一次退出（第二次 Ctrl+C、再打 `/exit`）也算确认。

## 三、按 457 逐条对照提出的六处（协调会话）

1. 前台派出的结果没有信任说明、没有边界包装、派出方会话里不记条目：前台与后台改为同一份——附同一句信任说明、放进带随机串的边界之间、派出方的会话记录里记一条 `pigeon.agent-message`（kind 为 result）。加了断言。
2. 回看时仍按前缀认程序通知，新的传话会被当成使用者的话、成为回退点、进 `/resume` 列表的"第一句话"：进模型的传话消息本身带结构化标记（消息对象上的 `pigeonAgentMessage`，记谁发给谁、哪一种；随消息存进会话记录，交给模型之前去掉，同开工状态块的 `pigeonStatus`），回看历史、会话回退（`humanInputText`）与 `/resume` 列表按标记认；同时每条传话照旧在收件方记 `pigeon.agent-message`。旧前缀那几行只留给旧会话（477）。加了测试：后台交回的结果在回看里显示成系统行、不算人说的话、不成为回退点。
3. 名字加序号后可能超过 40 个字符：加序号时截短原名，结果至多 40 个字符（按类型起名同样）。加了测试。
4. 每派一个子 agent，MCP 的启动问题再报一遍：子 agent 的 MCP 提示里，派出方开会话时已经报过的（沿用的连接照样算出来）不再报，只报新的。
5. 停下等审批的子 agent 时挂着的审批要自动撤回：审批请求带撤回信号（子 agent 的运行面每次被叫停即撤回、换一个新信号）；已在审批区的收掉，消息区留一行暗色结论 `withdrawn: <路径> was stopped`，按撤回收口、模型收到"请求已撤回"的拒绝；还在排队的不再上审批区。释放一批时那 5 秒等待保留。加了测试。
6. 死代码与 worker 字样：`/worktrees` 的 `liveWorkers` 参数删掉（在用改看在用锁，测试随之改）；`workerStartRefFor`、`WORKER_START_REF_PREFIX` 改名 `worktreeStartRefFor`、`WORKTREE_START_REF_PREFIX`（引用目录名 `refs/pigeon/worker-start/` 沿用，旧的照样认得、删得掉）；`execution/worker-overlay.ts` 改名 `worktree-overlay.ts`、`overlayWorkerChanges` 改名 `overlayWorktreeChanges`（面板会话的 `/take` 在用）。

可以接受、写明即可的几处：

- 完成通知第一行带一句状态（`finished`、`failed: <原因>`、`was stopped`）：派出方要知道成败，只是一句，不算结构化交回（480 写明）。
- 通用类型不给记忆写入、`enter_worktree` 与任务清单（480）。
- 带上下文起步记的是复制条数 `inheritedEntries`，不记分叉点。由它算分叉点：子 agent 会话文件开头的这么多条是派出方当时对话的副本（截到派出它的那条助手消息之前），消息原样复制、时间戳不变；派出方会话主分支里与复制段最后一条消息时间戳与内容都相同的那一条即分叉点（派出方压缩过的，复制段开头是压缩摘要，照样按最后一条对）。复制段之后的条目都是子 agent 自己的。
- 进程内送达保留限流、去重、待读上限（457 留给进程内通信用）。
- 并发上限满时，交给停着的子 agent 的东西（下层交回的结果、后台作业结束的通知）先留着，有子 agent 停下空出位置再按先后叫醒：这是消息排队，不是派出排队。不会互相等死：留着的只等"在跑的个数降下来"，而在跑的子 agent 从不等留着的那些——派出（前台、后台）撞上限一律当场拒绝、不排队，发给停着的子 agent 的消息撞上限同样当场拒绝；在跑的那些各自跑完即空出位置。
